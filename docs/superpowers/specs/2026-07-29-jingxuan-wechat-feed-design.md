# 京宣参阅消息公众号采集与网页设计

日期：2026-07-29

## 一、目标

利用腾讯云服务器上已经运行的 `wechat-article-exporter`，每 10 分钟查询指定公众号的最新文章，将最近 10 天的文章数据保存到 `im-xjh/zksk` 仓库，并通过 GitHub Pages 提供一个可直接在浏览器中打开的文章列表。

系统服务于人工发现选题。网页只负责降低查看 JSON 的操作成本，不承担阅读管理、选题分析或报送流程。

## 二、范围

第一版包含：

- 指定公众号清单，初始数量为 19 个，后续可扩充。
- 每 10 分钟执行一轮查询。
- 首次运行仅回填最近 10 天的文章。
- 后续始终只保留最近 10 天的文章。
- 文章按发布时间倒序写入 JSON，网页也按相同顺序展示。
- 发现文章集合发生变化时更新 JSON 并提交到 `zksk`。
- GitHub Pages 展示更新时间、文章数量、公众号、发布时间、标题、摘要和原文链接。

第一版不包含：

- 正文下载。
- CSV 输出。
- 大模型分析和选题推荐。
- 已读、收藏、候选选题、已报送等交互状态。
- 用户登录、权限系统和跨设备状态同步。
- Cubox、Notion、Telegram 等下游发布。

## 三、总体架构

```text
腾讯云 wechat-article-exporter
          ↓ 本地 Docker 网络
jingxuan-wechat-collector
          ↓ 查询、规范化、去重、保留最近 10 天
服务器 SQLite 运行状态
          ↓ 内容发生变化时通过 GitHub API 提交
im-xjh/zksk: docs/jingxuan/feed.json
          ↓ GitHub Pages
https://im-xjh.github.io/zksk/jingxuan/
```

新增采集器作为独立容器部署在服务器 `/opt/wechat-article-exporter` 下，共用 exporter 的 Docker 网络和登录态目录。现有 `wechat-cubox-sync`、全文抓取、日报及其他下游保持不变。

## 四、仓库文件

计划新增：

```text
京宣参阅消息/公众号采集/
├── accounts.json
├── collector.py
├── requirements.txt
└── tests/

docs/
├── .nojekyll
└── jingxuan/
    ├── index.html
    ├── app.js
    ├── style.css
    └── feed.json
```

`accounts.json` 只保存公众号名称和 `fakeid`。`feed.json` 是网页的唯一数据源，也是采集结果在 GitHub 中的正式存储文件。

GitHub Pages 从 `main` 分支的 `/docs` 目录发布。网页使用原生 HTML、CSS 和 JavaScript，不引入前端框架或构建工具。

## 五、数据格式

`feed.json` 顶层结构：

```json
{
  "version": 1,
  "generated_at": "2026-07-29T10:20:00+08:00",
  "window_days": 10,
  "article_count": 1,
  "articles": [
    {
      "id": "稳定文章标识",
      "account_name": "公众号名称",
      "title": "文章标题",
      "summary": "文章摘要",
      "published_at": "2026-07-29T09:30:00+08:00",
      "url": "https://mp.weixin.qq.com/s/..."
    }
  ]
}
```

约束：

- `url` 为主要去重键。
- `aid` 仅在服务器 SQLite 中作为辅助去重信息，不写入公开网页数据。
- `id` 由文章 URL 生成稳定哈希，网页不依赖数组下标。
- `articles` 按 `published_at` 从新到旧排列。
- JSON 使用 UTF-8，不包含登录密钥、Cookie、GitHub Token 或错误堆栈。

## 六、采集规则

### 首次运行

对清单中的每个公众号从第一页开始分页查询：

1. 接口返回文章后进行字段规范化。
2. 保留发布时间位于当前时刻之前 10 天以内的文章。
3. 当一页中出现早于时间窗口的文章、接口没有更多数据，或达到每个公众号 10 页的安全上限时停止。
4. 汇总全部公众号结果，以 URL 去重并按发布时间倒序写入 `feed.json`。

首次运行不导入 10 天以前的数据。

### 定时运行

每 10 分钟查询每个公众号第一页，每次请求之间默认间隔 15 秒。单轮完成后：

1. 将新增文章合并进服务器 SQLite。
2. 从 SQLite 选取最近 10 天文章。
3. 生成候选 `feed.json`。
4. 文章集合或展示字段发生变化时提交到 GitHub。
5. 没有变化时不更新 `generated_at`，也不产生 GitHub 提交。

文章超过 10 天后会从 `feed.json` 移除。移除造成内容变化时正常提交。

## 七、网页行为

网页加载 `feed.json` 后直接渲染文章列表：

- 页面顶部显示“最近更新时间”和“最近 10 天共 N 篇”。
- 每篇文章显示公众号名称、发布时间、标题和摘要。
- 点击标题在新标签页打开微信原文。
- 最新文章显示在最上方。
- 手机和桌面浏览器均可正常阅读。
- JSON 加载失败时显示明确错误和重试提示。
- 页面不保存 Cookie、Local Storage 或任何用户状态。

刷新浏览器页面即可读取 GitHub Pages 已发布的最新数据。

## 八、调度、频控与故障

- 19 个公众号按 15 秒间隔查询，一轮约 4 分 45 秒，可在 10 分钟周期内完成。
- 自建 exporter 不受公共站点每分钟 5 次的站点额度约束，但仍受微信后台频控。
- 微信返回频控错误时采用指数退避，不提高并发绕过限制。
- 登录态失效时本轮失败，保留 GitHub 中已有 `feed.json`，日志提示需要重新扫码。
- GitHub 提交失败时保留服务器 SQLite 状态，下轮重试。
- 新采集器每轮开始前读取现有微信同步 SQLite 的 `runs` 表；发现最近两小时内存在 `finished_at` 为空的任务时跳过本轮，避免共用登录态并发查询，下一轮自动补采。
- 公众号数量扩大后，如果一轮无法在 10 分钟内完成，应延长轮询周期或分批轮转，不启用高并发请求。

## 九、安全与公开边界

- `zksk` 当前为公开仓库，因此公众号清单、文章标题、摘要、发布时间和链接均为公开数据。
- exporter 登录态只保存在服务器现有 Cookie 目录。
- GitHub 写入令牌只保存在服务器 `.env`，不进入仓库、JSON、网页或日志。
- 正式运行使用仅允许写入 `im-xjh/zksk` 仓库内容的细粒度令牌。

## 十、验证标准

实现完成需满足：

1. 使用测试公众号清单执行首次同步，`feed.json` 中不存在 10 天以前的文章。
2. 同一批数据重复执行不会产生重复文章或新的 GitHub 提交。
3. 模拟新增文章后，JSON 出现该文章且位于正确倒序位置。
4. 模拟文章超过 10 天后，JSON 会移除该文章。
5. 网页能正确显示 JSON 中的全部文章并打开原文链接。
6. 手机和桌面宽度下没有横向溢出。
7. 登录失效、频控和 GitHub 写入失败均不会覆盖最后一次有效 JSON。
8. GitHub Pages 地址可从不同设备直接访问并看到相同内容。

## 十一、实施边界

本设计批准后再编写实施计划。实施阶段不得增加交互状态、正文抓取、AI 分析、数据库网站或其他发布渠道；新增需求另行设计。
