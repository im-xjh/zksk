# 公众号文章采集系统实施记录

更新时间：2026年7月30日

## 一、最终需求

本系统用于集中查看新闻类微信公众号最近发布的文章，为人工发现选题提供入口。当前确定的范围如下：

- 云服务器每10分钟轮询一次公众号。
- 第一次运行只同步最近1天，之后也只保留向前24小时内的文章。
- 数据写入中科数科自己的 GitHub 仓库 `im-xjh/zksk`。
- GitHub Pages 将 JSON 映射为可以直接打开的网页，文章按发布时间倒序排列。
- 页面只负责展示和跳转原文，不记录已读、报送或选题状态。
- 仓库已导入19项公众号清单。清单为空时程序必须拒绝运行，不能发布空数据覆盖已有内容。
- 云服务器复用已经登录并运行的 `wechat-article-exporter`，不另建登录系统。

公开仓库和 GitHub Pages 上的文章标题、公众号名称、摘要、发布时间及链接均为公开数据。GitHub Token、导出器登录文件、服务器状态库不得进入仓库。

## 二、已经落地的架构

```text
云服务器上的 wechat-article-exporter
        │
        │ 查询已关注公众号文章
        ▼
jingxuan-wechat-collector 容器
        │
        ├─ SQLite：保存去重状态
        │
        └─ GitHub Contents API：仅在内容变化时更新
                         │
                         ▼
              docs/jingxuan/feed.json
                         │
                         ▼
                  GitHub Pages 网页
```

采集器是独立 Compose 项目，项目名为 `jingxuan-wechat-collector`。它接入导出器已有的 `wechat-article-exporter_default` Docker 网络，并采用以下挂载：

- `/opt/wechat-article-exporter/data/kv/cookie`：只读，用于取得最新的导出器授权键文件名。
- `/opt/wechat-article-exporter/sync-state`：只读，用于避免与现有同步任务同时查询。
- `/opt/jingxuan-wechat-collector/state`：采集器独享的可写 SQLite 状态目录。
- `/opt/jingxuan-wechat-collector/accounts.json`：只读的公众号清单。

容器及镜像内进程均使用 `10001:10001` 身份运行。服务器目标目录已经建立，状态目录权限已经按该身份配置。空清单会阻止采集和发布，但不会自动阻止 Compose 重启策略；当前清单导入后仍等待首次同步和常驻运行验收。

`feed.json` 的固定结构如下：

```json
{
  "version": 1,
  "generated_at": null,
  "window_days": 1,
  "article_count": 0,
  "articles": []
}
```

正式文章包含 `id`、`account_name`、`title`、`summary`、`published_at` 和 `url` 六个字段。页面只接受 `https://mp.weixin.qq.com/` 链接，所有文本经过 HTML 转义。

## 四、运行规则

1. 定时循环每600秒开始一轮，单轮耗时会从下一次等待中扣除。
2. 公众号之间固定等待15秒，降低触发频率控制的概率。
3. 首次运行使用 `once --initial`，每个公众号最多翻10页，遇到向前24小时的窗口边界后停止。
4. 日常轮询每个公众号读取最新一页。
5. SQLite 以文章 URL 为唯一键去重，生成 Feed 时排除早于向前24小时及晚于当前时间的记录。
6. Feed 按发布时间倒序生成，只在文章内容发生变化时提交 GitHub。
7. 首次同步只要有任一公众号失败，就不发布不完整 Feed，并返回非零退出码。
8. 日常轮询遇到单个账号失败时保留已有数据；全部失败且没有历史数据时不发布。
9. 登录过期、持续限频、GitHub 网络异常及配置错误只输出安全错误类别，Token 不进入日志。
10. 检测到既有同步任务正在运行时，本轮主动跳过，避免两个任务同时请求导出器。

云服务器没有解除上游平台的频率控制。它提供全天在线和稳定调度能力，调用次数仍受导出器及微信接口约束。15秒账号间隔、遇限频后的5秒、10秒、20秒、40秒退避以及10分钟轮询共同控制请求频率。

## 五、公众号清单契约

当前 `accounts.json` 已写入19项正式账号清单，字段仅含 `nickname` 与 `fakeid`。下列为虚构示例：

```json
{
  "version": 1,
  "accounts": [
    {
      "nickname": "示例公众号",
      "fakeid": "example-fakeid"
    }
  ]
}
```

每项必须严格且仅包含 `nickname` 与 `fakeid`，两个字段均须为非空字符串，且 `fakeid` 不能重复。清单为空、JSON 格式错误、字段缺失、包含额外字段或出现重复时，程序会在发起网络请求前退出。

## 六、实施和审查记录

系统按数据模型、状态库、导出器客户端、GitHub 发布、采集调度、静态网页和容器部署七个模块依次完成。每个模块先建立测试，再实现代码，并分别经过规格审查和代码质量审查。

部署前审查发现并修正了以下问题：

- 排除发布时间晚于当前时间的异常记录。
- 固定 Feed 的 `version` 为1、`window_days` 为1，网页执行同样的严格校验。
- 首次同步出现任一账号错误时禁止发布部分结果。
- 定时循环捕获可预期异常，并维持以每轮起点计算的600秒周期。
- GitHub GET、PUT 网络异常统一转换为安全错误，命令行不输出回溯和敏感请求信息。
- GitHub API 错误信息中的 Token 会被替换为 `[REDACTED]`。
- 正式清单字段统一为 `nickname`，兼容 `name` 且由 `nickname` 优先。
- 1天窗口改为不可偏离的固定配置。
- Docker Hub 在腾讯云超时后，基础镜像切换到服务器既有项目采用的 `docker.1ms.run` 镜像源，Python 依赖切换到同一服务器既有项目采用的清华镜像。

最终本地自动化验证结果：

- Python：65项测试通过。
- Node.js：10项测试通过。
- Python 全模块编译通过。
- Docker Compose 配置解析通过。
- Git 差异格式检查通过。

独立部署审查未发现 Critical 或 Important 问题。一个已知的轻微边界是：首次同步遇到缺少链接的旧记录时，程序可能额外翻页，最多仍受10页上限控制，不会把无链接记录写入 Feed。

## 七、服务器预部署状态

服务器目录为 `/opt/jingxuan-wechat-collector`。项目文件已经同步，`state` 目录已经创建并归属 `10001:10001`、权限为 `0750`，Compose 配置已经使用现有导出器环境文件解析通过。

最终 Dockerfile 已在腾讯云完成真实构建，镜像为 `jingxuan-wechat-collector:local`。容器内实测身份为 `uid=10001(app)`、`gid=10001(app)`，入口为 `python /app/collector.py run`。使用空清单执行 `validate-accounts` 返回 `ConfigurationError` 和退出码1；一次性验证容器已经自动删除，常驻及停止状态的同名容器数量均为0。

采集服务当前不会常驻启动。此状态是有意设置的双重安全门：部署人员没有执行 `up -d`；公众号清单为空时，`validate-accounts` 返回非零，不能进入首次同步或定时循环。若误执行 `up -d`，`restart: unless-stopped` 会让配置错误的容器反复退出并重启，因此空清单阶段仍需人工保持服务未启动。

## 八、清单导入后的唯一激活流程

19项公众号名称和 `fakeid` 已导入后，执行人员按以下顺序完成激活：

1. 将清单写入仓库内的 `accounts.json`。
2. 在本地运行清单校验及全量测试。
3. 提交并推送 `main` 分支。
4. 将更新后的采集目录同步到 `/opt/jingxuan-wechat-collector`，保留服务器 `state` 目录。
5. 在服务器运行 `docker compose config --quiet`，再构建当前版本镜像。
6. 在服务器容器内执行 `python /app/collector.py validate-accounts`。
7. 执行一次 `python /app/collector.py once --initial`。
8. 核对首次 Feed：只含向前24小时、时间倒序、标识唯一、字段完整，抽查文章链接可以打开。
9. 等待 `main:/docs` 的 GitHub Pages 发布完成，核对网页已显示同一批数据。若 Pages 配置被关闭，先重新将发布源设为 `main:/docs`。
10. 执行 `docker compose up -d` 启动每10分钟轮询。
11. 查看首轮常驻日志和容器状态，确认没有登录失效、频率控制或 GitHub 发布错误。

只要提供符合上述契约的公众号清单并通知运行，执行人员即可完成这套流程，无需重新设计或开发。

## 九、维护命令

以下命令均在服务器 `/opt/jingxuan-wechat-collector` 目录执行，并使用 `/opt/wechat-article-exporter/.env` 提供已有的 `GITHUB_TOKEN`。命令及日志中不得打印环境文件内容。

```bash
# 解析部署配置
docker compose --env-file /opt/wechat-article-exporter/.env config --quiet

# 构建镜像
docker compose --env-file /opt/wechat-article-exporter/.env build

# 校验公众号清单
docker compose --env-file /opt/wechat-article-exporter/.env run --rm \
  jingxuan-wechat-collector python /app/collector.py validate-accounts

# 首次同步
docker compose --env-file /opt/wechat-article-exporter/.env run --rm \
  jingxuan-wechat-collector python /app/collector.py once --initial

# 启动定时采集
docker compose --env-file /opt/wechat-article-exporter/.env up -d

# 查看状态与最近日志
docker compose --env-file /opt/wechat-article-exporter/.env ps
docker compose --env-file /opt/wechat-article-exporter/.env logs --tail=100

# 停止定时采集
docker compose --env-file /opt/wechat-article-exporter/.env down
```

如果日志出现 `SessionExpired`，需要先在现有 `wechat-article-exporter` 完成重新登录，再手动执行一轮 `once` 验证。采集器会自动选用只读 Cookie 目录中更新时间最新的授权键文件名。
